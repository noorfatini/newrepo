# Day 5 Exercise 5.2: REST API Design - Answers

## Scenario Recap
I am designing part of an API for an event booking system. There are two main resources here:

- **events** — the events people can book
- **bookings** — a record of someone booking a seat/spot at an event

---

## API Specification Table

| Resource | Method | Endpoint | Purpose | Request Body Needed? | Success Status | Possible Error Status |
|---|---|---|---|---|---:|---:|
| Events | GET | /api/events | View all available events | No | 200 | 500 |
| Events | GET | /api/events/{id} | View details of one event | No | 200 | 404 |
| Bookings | POST | /api/bookings | Create a new booking for an event | Yes | 201 | 400, 404, 409 |
| Bookings | GET | /api/bookings | View all bookings | No | 200 | 500 |
| Bookings | GET | /api/bookings/{id} | View details of one booking | No | 200 | 404 |
| Bookings | PATCH | /api/bookings/{id} | Cancel a booking (update its status to cancelled) | Yes | 200 | 404, 409 |

I used `PATCH` instead of `DELETE` for cancelling a booking, because in real life you usually don't want to fully delete a booking record — you want to keep it as history, just marked as `CANCELLED`. That's also why "booking is already cancelled" makes sense as an error case later — the booking still exists, just in a cancelled state.

---

## Request Body Planning

| Endpoint | Request Body Description |
|---|---|
| POST /api/bookings | The id of the event being booked, the customer's name and email, and the number of seats being booked |
| PATCH /api/bookings/{id} | The new status for the booking, e.g. `"status": "CANCELLED"` |

---

## Error Planning

| Error Case | Related Endpoint | Suitable Status Code | Explanation |
|---|---|---:|---|
| Required field missing (e.g. no eventId, or no customer name) | POST /api/bookings | 400 | The server cannot create a booking without knowing what to book or who is booking, so it rejects the request as invalid input. |
| Event does not exist | GET /api/events/{id}, POST /api/bookings | 404 | If someone asks for an event id that isn't in the system, or tries to book against an event id that doesn't exist, there is nothing to return or book. |
| Event is fully booked | POST /api/bookings | 409 | The event exists, the request is valid, but there are no seats left. This is a conflict between what the user wants and the current state of the event, not a bad request. |
| Booking does not exist | GET /api/bookings/{id}, PATCH /api/bookings/{id} | 404 | If someone tries to view or cancel a booking id that isn't in the system, the server has nothing to return or update. |
| Booking is already cancelled | PATCH /api/bookings/{id} | 409 | The booking exists, but it's already in a cancelled state, so cancelling it again is a conflict with its current state, not a normal success. |

---

## Why My Endpoint Names Follow REST Principles

All my endpoints are named after the **resource** (`events`, `bookings`), not after an action. For example, I used `POST /api/bookings` instead of `/createBooking`, and `PATCH /api/bookings/{id}` instead of `/cancelBooking`. The action (create, view, cancel) is expressed through the **HTTP method**, not through the URL text. This is the main REST rule: the URL says *what thing* you are working with, and the method says *what you are doing to it*.

I also used the id inside the URL path (`/api/bookings/{id}`) to point at one specific item, instead of something like `/getBookingById?id=123`, which mixes an action name into the URL. And I didn't make everything `POST` — I used `GET` for reading data, `POST` for creating a new booking, and `PATCH` for updating an existing booking's status, so each method matches what it's actually meant to do.
